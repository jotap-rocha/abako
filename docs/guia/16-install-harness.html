Instalando o Harness

Do projeto zerado ao harness completo

install bootstrap canonical projetos filosofia
canônico → /install-harness → projeto alvo → customização → produção

O que é o harness canônico

Fonte única de verdade para todos os projetos. O canônico não é copiado — é referenciado e instanciado.

agent-harness-canonico/ → /install-harness → projeto-alvo/.claude/ → instância customizada

O que o canônico TEM

agents/ — especialistas reutilizáveis
skills/ — comandos /slash prontos
kb/ — bases de conhecimento curadas
rules/ — invariantes e contrato de entrega
docs/guia/ — 16 guias de referência
settings.json — hooks e permissões

O que o projeto GANHA

CLAUDE.md com stack real do projeto
CONTEXT.md com terminologia do domínio
Hooks adaptados à stack detectada
Skills filtradas (só as relevantes)
KB do domínio preenchida pelo time
harness-manifest.json (memória da install)
"Canônico = framework. Projeto = instância."

Os 3 cenários de instalação

A skill detecta o estado atual e age de forma diferente em cada cenário.

NOVO SEM_HARNESS INCOMPLETO
O que existe antes Pasta completamente vazia — nenhum .claude/ .claude/ parcial ou CLAUDE.md avulso sem manifest harness-manifest.json presente mas desatualizado
O que o install faz Scaffolding completo + cópia integral do canônico Instala o que falta; lê e preserva o que existe Compara manifest vs canônico; atualiza só o não-customizado
O que fica intocado Nada a preservar — slate em branco Todos os arquivos já existentes (nunca sobrescreve sem ok) Artefatos marcados "customized": true no manifest

Regra universal

Em todos os cenários: a skill mostra o Install Plan e aguarda confirmacao explícita antes de escrever qualquer arquivo no disco.

Cenário 1 — Projeto Zerado

NOVO

Pasta sem nenhum .claude/. A skill faz tudo do zero.

1

Detecta ausência de .claude/

Verifica se o diretório existe. Ausência = cenário NOVO confirmado.

2

Lê pyproject.toml / package.json para detectar stack

FastAPI, Django, Next.js, LangGraph, Supabase — cada stack ativa artefatos diferentes.

3

Mapeia stack → artefatos relevantes

FastAPI → hooks ruff+mypy+pytest. LangGraph → skills langgraph-*. Supabase → kb/supabase/.

4

Mostra Install Plan e aguarda confirmação

Lista completa do que será criado. Zero escrita antes do "ok".

5

Copia do canônico + gera projeto-específicos

Artefatos canônicos copiados; CLAUDE.md e CONTEXT.md gerados com stack real.

Output da instalação

CLAUDE.mdAGENTS.mdCONTEXT.mdHANDOFF.md settings.jsonagents/skills/kb/harness-manifest.json

Cenário 2 — Existente sem Harness

SEM_HARNESS

.claude/ pode ter arquivos avulsos — CLAUDE.md escrito à mão, settings parcial, nenhum manifest.

O que a skill faz

1. Lê todos os arquivos existentes em .claude/

2. Calcula diff entre o que existe e o que o canônico fornece

3. Exibe tabela de 3 colunas antes de qualquer ação

As 3 colunas do diff

JÁ EXISTEnão toca
NOVOvai instalar do canônico
SKIPstack não detectada
[JÁ EXISTE]  .claude/CLAUDE.md              (preservado — não modificado)
[JÁ EXISTE]  .claude/settings.json          (preservado — não modificado)
[NOVO]       .claude/agents/dev/revisor-codigo.md
[NOVO]       .claude/skills/validar.md
[NOVO]       .claude/kb/backend/fastapi.md
[SKIP]       .claude/kb/supabase/            (Supabase não detectado na stack)
[SKIP]       .claude/skills/langgraph-*.md  (LangGraph não detectado)
!

Anti-padrao: nunca sobrescrever

Arquivo existente = intocável sem confirmação explícita do usuário. Mesmo que o canônico tenha uma versão mais nova.

Cenário 3 — Harness Incompleto

INCOMPLETO

harness-manifest.json presente. A skill compara o manifest com o estado atual do canônico.

ATUALIZAR

Canônico evoluiu desde a última install. Arquivo não foi customizado pelo projeto. Seguro atualizar automaticamente.

MANTER

Arquivo customizado pelo projeto ("customized": true no manifest). Nunca tocar — mesmo que o canônico tenha evoluído.

NOVO

Artefato adicionado ao canônico após a última install. Não existe no projeto ainda. Será instalado com confirmação.

// trecho de harness-manifest.json
{
  "canonical_path": "",
  "installed_at": "2026-05-10T14:32:00Z",
  "artefacts": [
    { "path": ".claude/agents/dev/revisor-codigo.md", "source": "canonical", "customized": false },
    { "path": "CLAUDE.md",                      "source": "generated", "customized": true  },
    { "path": "CONTEXT.md",                     "source": "generated", "customized": true  }
  ]
}

"customized": false = canônico pode atualizar. "customized": true = projeto é dono — harness não toca.

O Install Plan

Anatomia do plano exibido antes de qualquer escrita no disco. Revisabilidade antes de execução.

COPIAR do canônico

Artefatos copiados bit a bit do canônico — agents, skills, kb, rules selecionadas pela stack.

GERAR (projeto-específico)

CLAUDE.md, CONTEXT.md skeleton, harness-manifest.json — gerados com dados reais do projeto (stack, nome, paths).

PULAR (stack não detectada)

Artefatos de stacks ausentes não são copiados — evita ruído de tecnologias irrelevantes para o projeto.

NAO TOCAR (customizado)

Arquivos marcados como customizados ou já existentes sem manifest — listados para visibilidade mas intocáveis.

"Mostrar o plano antes de agir é a diferença entre uma ferramenta que colabora e uma que surpreende."
— princípio de reversibilidade

Por que confirmar antes de agir

Reversibilidade: o usuário pode ajustar o plano (excluir itens, alterar destinos) antes de qualquer mudança real. Alinha entendimento antes de gerar.

O manifest

.claude/harness-manifest.json — memória da instalação. Habilita atualizações seletivas em futuras execuções.

// .claude/harness-manifest.json — estrutura completa
{
  "version": "1.0",
  "canonical_path": "",
  "installed_at": "2026-06-27T09:00:00Z",
  "project_stack": ["fastapi", "langgraph", "postgres"],
  "artefacts": [
    {
      "path": ".claude/agents/dev/revisor-codigo.md",
      "source": "canonical",   // "canonical" | "generated"
      "canonical_hash": "a3f9b12c",
      "customized": false           // true = projeto editou, nunca tocar
    },
    {
      "path": "CLAUDE.md",
      "source": "generated",
      "customized": true
    }
  ]
}

Quem escreve

/install-harness — cria na primeira run e atualiza em cada reinstall. Nunca editado manualmente (exceto para marcar customized: true).

Quem lê

/install-harness em futuras atualizações. /sync-context para detectar deriva entre projeto e canônico. revisor-codigo para verificar integridade.

Após a instalação — próximos passos

A install entrega a estrutura. O conteúdo real vem do diálogo com quem conhece o domínio.

/install-harness → /grill-with-docs → /grill-me → revisar hooks → /validar
1

/grill-with-docs

Preenche CONTEXT.md com terminologia real do domínio — lendo docs, código, ADRs do projeto.

2

/grill-me

Dialoga com o especialista para refinar CLAUDE.md com invariantes reais do negócio.

3

Revisar hooks no settings.json

Confirmar que PostToolUse e gate Stop batem com a stack e os paths reais do projeto.

4

/validar — gate verde

Ruff + mypy + pytest. O harness só está pronto quando o gate passa na primeira execução.

!

CONTEXT.md vem vazio do install

Não invente termos, fluxos ou entidades. O conteúdo correto vem do especialista de domínio via /grill-with-docs + /grill-me. Inventar = ruído que polui toda sessão futura.

O ciclo completo

O harness não é instalado uma vez — é um ciclo vivo entre canônico, projeto e produção.

canônico evolui → /install-harness propaga → projeto customiza → agent executa → falha real em prod → vira regra/skill/KB no canônico
Camada Responsável O que mantém O que nunca faz
Canônico Time de plataforma Framework, skills, KB genéricos, guias Conter terminologia de domínio específico
Projeto Time de produto CLAUDE.md, CONTEXT.md, invariantes do negócio Reescrever artefatos canônicos à mão
Agent Claude (runtime) Execução, traces, HANDOFF.md entre sessões Alterar manifest ou customizar sem instrução
"O harness aperta um dente a cada erro — a falha de hoje é a regra de amanhã."
— princípio de melhoria contínua do canônico
