Testing Patterns

Pirâmide, pytest, vitest e fronteiras de mock

Pirâmide pytest fixtures Factory pattern vitest Mock boundaries

"Teste o comportamento, não a implementação. Mock o que for externo; use o real para o que for seu."

Estratégia

A Pirâmide — 70 / 25 / 5

70%

Unit

Lógica pura. Todo I/O externo mockado. Roda em milissegundos.

25%

Integration

Banco real, LLM mockado. Verifica contratos entre camadas.

5%

E2E

Playwright. Caminho feliz apenas. Detecta regressão de UI.

Camada O que testa O que mocka Velocidade Quando escrever
Unit Funções, regras de negócio, transformações LLM, banco, HTTP, Qdrant, filesystem < 1 ms Sempre — TDD ou junto com a feature
Integration Repositórios, services com banco, grafo LangGraph LLM, HTTP externo 100 ms – 2 s Para cada boundary com infra real
E2E Fluxo completo do usuário Nada (ou serviços externos opcionais) 5 – 30 s Caminho feliz + 1 caminho de erro crítico

Regra prática

Se o teste levou mais de 2 s para rodar, provavelmente está no nível errado da pirâmide — ou está fazendo I/O onde não deveria.

Fronteiras

O que mockar — e o que não mockar

Dependência Unit Integration Motivo
LLM (OpenAI, Anthropic) sempre mockar sempre mockar Custo, latência, não-determinismo, rate limit
HTTP externo (APIs) mockar mockar Evita dependência de disponibilidade externa
Banco de dados (Postgres) mock em unit real em integration Queries, migrações e constraints precisam de banco real
Qdrant mock em unit real em integration Filtros de payload e ranking precisam do engine real
Filesystem real real Simples, determinístico, sem estado compartilhado

Lição do workshop

Um mock de banco passou em CI por 3 sprints. Na primeira migração real em prod, a constraint UNIQUE(tenant_id, titulo) explodiu — o mock não a conhecia. Banco real em integration não é opcional.

Critério de decisão

Se a dependência tem estado persistido, schema ou comportamento não-trivial — use o real em integration. Se tem custo, latência ou não-determinismo — mock.

pytest

Fixtures — Scopes

Scope Cria uma vez por Usar para
function Cada teste Transação com rollback, estado isolado
class Classe de testes Contexto compartilhado por grupo de testes
module Arquivo .py Setup caro mas não global (seed de tabela)
session Toda a suíte Pool de conexões, containers Docker

Padrão recomendado

Pool em session, transação com rollback em function. Cada teste começa limpo sem recriar o banco.

# tests/conftest.py
import pytest
import asyncpg

@pytest.fixture(scope="session")
async def db_pool():
    pool = await asyncpg.create_pool(
        dsn="postgresql://test:test@localhost/testdb"
    )
    yield pool
    await pool.close()

@pytest.fixture(scope="function")
async def db_conn(db_pool):
    async with db_pool.acquire() as conn:
        # Abre transação — rollback ao sair
        tr = conn.transaction()
        await tr.start()
        yield conn
        await tr.rollback()
Factory Pattern

Factory Fixtures

# tests/conftest.py
TENANT_A = "tenant-aaa-111"
TENANT_B = "tenant-bbb-222"

@pytest.fixture
def make_caso(db_conn):
    """Retorna função de criação com defaults."""
    async def _factory(
        tenant_id: str = TENANT_A,
        titulo: str = "Caso de teste",
        status: str = "aberto",
        **kwargs,
    ):
        row = await db_conn.fetchrow(
            """INSERT INTO casos
               (tenant_id, titulo, status)
               VALUES ($1, $2, $3)
               RETURNING *""",
            tenant_id, titulo, status,
        )
        return dict(row)
    return _factory

# No teste
async def test_isolamento_tenant(make_caso):
    caso_a = await make_caso(tenant_id=TENANT_A)
    caso_b = await make_caso(tenant_id=TENANT_B)
    assert caso_a["tenant_id"] != caso_b["tenant_id"]

Por que factory > dados hard-coded

  • Parâmetros opcionais com defaults sensatos
  • Reutilizável em toda a suíte sem duplicação
  • Testes declarativos: o teste expressa o que importa
  • Fácil de evoluir quando o schema muda

Constantes no conftest

TENANT_A e TENANT_B em tests/conftest.py — importáveis em qualquer módulo de teste sem reimportar o fixture.

Mocks

Mock Fixtures — Composição

# tests/unit/conftest.py
from unittest.mock import AsyncMock, MagicMock
import pytest

@pytest.fixture
def mock_llm():
    llm = AsyncMock()
    llm.ainvoke.return_value = AsyncMock(
        content="resposta mock"
    )
    return llm

@pytest.fixture
def mock_qdrant():
    qdrant = MagicMock()
    qdrant.search.return_value = []
    return qdrant

@pytest.fixture
def chat_service(mock_llm, mock_qdrant, db_conn):
    from app.services.chat import ChatService
    return ChatService(
        llm=mock_llm,
        qdrant=mock_qdrant,
        conn=db_conn,
    )

Hierarquia de conftest

tests/conftest.py

db_pool, db_conn, TENANT_A/B, make_caso

↓ tests/unit/conftest.py

mock_llm, mock_qdrant, chat_service

↓ tests/integration/conftest.py

llm real (opicional), qdrant real

Fixtures de escopo maior são herdadas. Unit herda db_conn do global mas substitui o LLM pelo mock.

Patterns

pytest — Patterns Essenciais

# pytest.ini / pyproject.toml
[tool.pytest.ini_options]
asyncio_mode = "auto"
addopts = "--cov=app --cov-fail-under=80"
markers = [
    "integration: marca testes de integração",
    "slow: testes lentos (> 2s)",
    "llm: requer chamada real ao LLM",
]

# Parametrize: casos felizes + edge cases
@pytest.mark.parametrize("query,esperado", [
    ("vendas do mês", "SELECT"),
    ("",              None),      # string vazia
    (None,            None),      # None
])
async def test_classify(query, esperado, chat_service):
    resultado = await chat_service.classify(query)
    assert resultado == esperado, (
        f"classify({query!r}) retornou {resultado!r}, esperado {esperado!r}"
    )

# Exceções com match de mensagem
def test_query_sem_limit(sql_validator):
    with pytest.raises(ValueError, match="LIMIT obrigatório"):
        sql_validator.validate("SELECT * FROM pedidos")

Markers em uso

  • -m "not integration" — só unit (CI rápido)
  • -m integration — testes com banco
  • -m "not slow" — exclui testes lentos
  • -m llm — requer API key real

assert com mensagem

Sempre inclua contexto no assert. Quando falhar às 2h, a mensagem salva o debug.

Coverage gate

--cov-fail-under=80 no gate impede que o PR passe com coverage abaixo do mínimo.

Frontend

vitest — Setup e Componentes

// vitest.config.ts
import { defineConfig } from 'vitest/config'

export default defineConfig({
  test: {
    environment: 'jsdom',
    setupFiles: ['./src/tests/setup.ts'],
    globals: true,
  },
})

// src/tests/setup.ts
import '@testing-library/jest-dom'
import { vi } from 'vitest'

vi.mock('@/lib/supabase', () => ({
  supabase: { from: vi.fn() }
}))

// Teste de componente — padrão AAA
import { render, screen } from '@testing-library/react'
import userEvent from '@testing-library/user-event'

it('exibe erro quando campo vazio', async () => {
  // Arrange
  render(<FormCaso />)
  // Act
  await userEvent.click(screen.getByRole('button', { name: /salvar/i }))
  // Assert
  expect(screen.getByRole('alert')).toBeInTheDocument()
})

getByRole > className

  • Reflete como o usuário percebe o UI
  • Valida acessibilidade implicitamente
  • Resistente a refactoring de estilos
  • Falha quando o role semântico muda — sinal real

Por que jsdom?

Simula DOM no Node sem browser. Suficiente para testar lógica de componente. Use Playwright apenas para E2E.

Hooks React

vitest — Hooks Customizados

import { renderHook, waitFor } from '@testing-library/react'
import { vi, expect, it } from 'vitest'
import { useCasos } from '@/hooks/useCasos'
import { supabase } from '@/lib/supabase'

it('carrega casos e limpa loading', async () => {
  // Mock chain: from().select().eq()
  const mockEq = vi.fn().mockResolvedValue({
    data: [{ id: '1', titulo: 'Fraude PIX' }],
    error: null,
  })
  const mockSelect = vi.fn().mockReturnValue({ eq: mockEq })
  vi.mocked(supabase.from).mockReturnValue({ select: mockSelect } as any)

  const { result } = renderHook(() => useCasos('tenant-123'))

  // Verifica estado inicial loading
  expect(result.current.loading).toBe(true)

  await waitFor(() => {
    expect(result.current.loading).toBe(false)
  })

  // Verifica dados retornados
  expect(result.current.casos).toHaveLength(1)
  expect(result.current.casos[0].titulo).toBe('Fraude PIX')
  expect(result.current.error).toBeNull()
})

Anti-padrão

Testar implementação em vez de comportamento:

// Ruim — testa detalhes internos
expect(hook.current._fetchFn)
  .toHaveBeenCalledWith(...)

// Bom — testa o que o usuário vê
expect(result.current.casos)
  .toHaveLength(1)

Estados a testar

  • loading: true no início
  • dados corretos após resolve
  • error preenchido após reject

Skill /gen-tests

Gera scaffolding de pytest e vitest a partir de um arquivo de código. Produz:

  • Fixtures de scope correto para o módulo
  • Factory fixtures para entidades do arquivo
  • Testes parametrizados com edge cases
  • Mock stubs para LLM e Qdrant

Gate hard no Stop hook

ruff check --fix backend ↓ mypy backend ↓ pytest -q ↓ coverage >= 80%

Se qualquer etapa falha, o agente não pode commitar. O gate é executado pelo hook — não pela memória do agente.
