Auth, RLS, Edge Functions, pgvector e Realtime

"Supabase não é uma abstração sobre Postgres — é Postgres, com Auth, RLS e APIs geradas ao redor."

Fundamentos

Por que Supabase

O que torna Supabase diferente

  • Postgres como core — não é abstração; você acessa SQL direto
  • Auth embutido — JWT assinado, magic link, OAuth; sem servidor extra
  • RLS no banco — políticas executam dentro do Postgres, não na app
  • Edge Functions — Deno, deploy em segundos, co-localizado com o banco
  • pgvector nativo — RAG sem infra separada; HNSW integrado
  • Realtime — subscriptions via WebSocket sobre mudanças na tabela

Quando escolher Supabase

Projetos com autenticação + dados relacionais + necessidade de RAG onde você quer Postgres real sem operar infra. Se você já tem FastAPI com Postgres separado, Supabase pode ser a camada de Auth + pgvector sem substituir o backend.

Autenticação

Auth — magic link e OAuth

usuário entra email → magic link enviado → confirm URL → session JWT 
import { createClient } from '@supabase/supabase-js'

const supabase = createClient(url, anonKey)

// Magic link — sem senha
const { error } = await supabase.auth.signInWithOtp({
  email: 'user@example.com',
  options: { emailRedirectTo: 'https://app.com/auth/callback' }
})

// OAuth — GitHub, Google, etc.
await supabase.auth.signInWithOAuth({
  provider: 'github',
  options: { redirectTo: 'https://app.com/auth/callback' }
})

// Claims customizados via hook no banco (pg function)
-- supabase_auth_admin.custom_access_token_hook(event jsonb)
-- adiciona app_metadata ao JWT

JWT gerado pelo Supabase

Contém: sub (user_id), role, email, app_metadata, user_metadata, aud, exp.

Disponível no banco via auth.uid() e auth.jwt() — usados nas políticas RLS.

Anti-padroes

  • Nunca confiar no user_id do body da request
  • Nunca usar service_role key no frontend
  • Nunca armazenar o JWT em localStorage sem HttpOnly cookie
  • Nunca verificar JWT somente no cliente

Session do lado servidor

Em Server Components / API routes: use createServerClient com cookies. O JWT é verificado server-side antes de qualquer query.

Segurança

RLS — Row Level Security

O que é RLS

Política executada dentro do Postgres antes de retornar qualquer linha. Não importa se o ataque bypassa a app — o banco bloqueia na camada de dado.

-- 1. Habilitar RLS na tabela
ALTER TABLE posts ENABLE ROW LEVEL SECURITY;

-- 2. Política de leitura: só o dono vê seus posts
CREATE POLICY "owner_read"
  ON posts FOR SELECT
  USING (user_id = auth.uid());

-- 3. Política de escrita: só o dono escreve
CREATE POLICY "owner_insert"
  ON posts FOR INSERT
  WITH CHECK (user_id = auth.uid());

-- auth.uid()  → UUID do usuário autenticado
-- auth.jwt()  → payload completo do JWT
-- auth.role() → 'anon' | 'authenticated' | custom
Operação Política Quem vê
SELECT USING Filtra linhas retornadas
INSERT WITH CHECK Valida linha antes de inserir
UPDATE USING + WITH CHECK Filtra alvo + valida novo valor
DELETE USING Filtra linhas que podem ser deletadas

auth.uid() vs auth.jwt()

auth.uid() — UUID do user. Mais rápido, preferido para comparar com FK.

auth.jwt() — payload completo. Use para claims customizados como org_id, role.

Sem policy + RLS habilitado = nenhuma linha retornada (deny-by-default).

Padroes RLS

4 padrões prontos para uso

1 — Pessoal (só dono)

-- User vê só seus próprios registros
CREATE POLICY "personal" ON notes
  FOR ALL USING (user_id = auth.uid())
  WITH CHECK (user_id = auth.uid());

2 — Multi-tenant (org_members)

-- User vê dados da sua organização
CREATE POLICY "tenant" ON documents
  FOR SELECT USING (
    org_id IN (
      SELECT org_id FROM org_members
      WHERE user_id = auth.uid()
    )
  );

3 — Público (todos leem)

-- Qualquer usuário (anon inclusive) lê
CREATE POLICY "public_read" ON products
  FOR SELECT
  USING (true);

-- Só autenticado escreve
CREATE POLICY "auth_write" ON products
  FOR INSERT
  WITH CHECK (auth.role() = 'authenticated');

4 — Compartilhado (owner + invited)

-- Dono ou convidado explícito lê
CREATE POLICY "shared" ON workspaces
  FOR SELECT USING (
    owner_id = auth.uid()
    OR auth.uid() = ANY(invited_ids)
  );

Verificar políticas ativas

SELECT tablename, policyname, cmd, qual, with_check
FROM pg_policies
WHERE schemaname = 'public'
ORDER BY tablename, policyname;
Serverless

Edge Functions — quando usar

Use Edge Function quando...

  • Webhook com verificação de assinatura (Stripe, GitHub)
  • Operação que precisa de secret não exposto ao cliente
  • CORS customizado para domínio específico
  • Proxy de API externa (OpenAI, SendGrid)
  • Trigger pós-insert com lógica complexa

Prefira FastAPI/backend quando...

  • Lógica de negócio complexa com testes unitários
  • Processamento CPU-intensivo ou streaming
  • Dependências Python/pip (Deno não suporta)
  • Grafo LangGraph — mantém no backend próprio
// supabase/functions/webhook-handler/index.ts
import { serve } from "https://deno.land/std/http/server.ts"
import { createClient } from 'https://esm.sh/@supabase/supabase-js'

serve(async (req) => {
  const secret = Deno.env.get('WEBHOOK_SECRET')   // env seguro
  const sig = req.headers.get('x-signature')
  if (!verifySignature(sig, secret)) {
    return new Response('Unauthorized', { status: 401 })
  }
  // processar payload...
  return new Response('OK', { status: 200 })
})

# Setup local
supabase functions new my-fn

# Testar local

# Deploy

# Env vars no deploy

  WEBHOOK_SECRET=xxx

Runtime: Deno

TypeScript nativo, sem node_modules. Imports via URL ou esm.sh. Cold start ~300ms. Timeout padrão 150s.

RAG

pgvector — RAG sobre Supabase

-- 1. Habilitar extensão
CREATE EXTENSION IF NOT EXISTS vector;

-- 2. Tabela com coluna de vetor (1536d = ada-002)
CREATE TABLE documents (
  id        uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  content   text,
  embedding vector(1536),
  metadata  jsonb,
  user_id   uuid REFERENCES auth.users
);

-- 3. Índice HNSW (busca aproximada, rápido)
CREATE INDEX ON documents
  USING hnsw (embedding vector_cosine_ops);

-- 4. Função match_documents para RPC
CREATE OR REPLACE FUNCTION match_documents(
  query_embedding vector(1536),
  match_threshold float,
  match_count     int
) RETURNS TABLE(id uuid, content text, similarity float)
AS $$
  SELECT id, content,
    1 - (embedding <=> query_embedding) AS similarity
  FROM documents
  WHERE 1 - (embedding <=> query_embedding) > match_threshold
  ORDER BY embedding <=> query_embedding
  LIMIT match_count;
$$ LANGUAGE sql;

Realtime

Realtime — subscriptions e presença

// Subscription com filtro de tabela + evento
const channel = supabase
  .channel('messages-room')
  .on('postgres_changes', {
    event:  'INSERT',         // INSERT | UPDATE | DELETE | *
    schema: 'public',
    table:  'messages',
    filter: `room_id=eq.${roomId}`
  }, (payload) => {
    setMessages(prev => [...prev, payload.new])
  })
  .subscribe()

// Presence — quem está online
await channel.track({ user_id: userId, status: 'online' })
channel.on('presence', { event: 'sync' }, () => {
  const state = channel.presenceState()
  setOnlineUsers(Object.keys(state))
})

// Broadcast — mensagem sem persistência
channel.on('broadcast', { event: 'typing' }, ({ payload }) => {
  showTypingIndicator(payload.user_id)
})
// Hook React reutilizável
function useRealtimeSubscription(table, filter, onInsert) {
  useEffect(() => {
    const ch = supabase.channel(`rt-${table}`)
      .on('postgres_changes',
        { event: 'INSERT', schema: 'public', table, filter },
        ({ new: row }) => onInsert(row))
      .subscribe()
    return () => supabase.removeChannel(ch)
  }, [table, filter])
}

3 modos Realtime

Postgres Changes — escuta mudanças em tabelas. Requer RLS habilitado na tabela.

Presence — rastreia estado de usuarios conectados. Key/value efêmero.

Broadcast — mensagens sem persistência. Latência baixa, sem gravar no banco.

Limitacoes

  • Nao usar para > 1000 clientes simultâneos no plano free
  • Postgres Changes exige tabela com RLS ativo
  • Filter de subscription não substitui RLS — complemente
  • Payload do evento nao inclui joins — busque dados extras separado

Limpar subscription

Sempre retorne supabase.removeChannel(ch) no cleanup do useEffect para evitar leak de conexão WebSocket.

Invariantes

Os 5 invariantes Supabase

ID Invariante O que garante O que proibe
SB-01 Client correto por contexto anon key no frontend; service_role key só em servidor/Edge Function com variável de ambiente. Expor service_role em código cliente, bundle JS, ou repositório.
SB-02 RLS em toda tabela Toda tabela no schema public com ENABLE ROW LEVEL SECURITY + ao menos uma policy. Tabela pública sem RLS; usar service_role para burlar políticas como atalho.
SB-03 JWT verificado server-side Em rotas de API próprias (FastAPI, Edge Function), verificar JWT com a secret antes de qualquer operação. Confiar em user_id do body da request; verificar JWT só no cliente.
SB-04 Secrets em env, nao em codigo SUPABASE_SERVICE_ROLE_KEY, JWT_SECRET apenas em variáveis de ambiente. Nunca em arquivo comitado. Hardcode de keys em .ts, .py ou qualquer arquivo versionado.
SB-05 Pre-filter tenant antes de semântico Em RAG com pgvector, aplicar filtro de org_id/user_id antes da busca por embedding. Busca vetorial global seguida de filtro por tenant — vaza contexto entre tenants via similaridade.

Checklist de auditoria rapida

SELECT tablename FROM pg_tables WHERE schemaname='public' — lista tabelas. Para cada uma: SELECT relrowsecurity FROM pg_class WHERE relname='tablename' deve retornar true.
