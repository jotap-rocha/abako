CLAUDE.md

O índice durável

Carregado em toda sessão. Deve ser curto — cada linha custa tokens de contexto. Só fatos que valem para o projeto inteiro.

O que vai aqui

  • Stack (linguagem, framework, stores)
  • Comandos de dev (subir, testar, validar)
  • Invariantes de SI e de produto
  • Mapa de KBs e rules
  • Onde fica o quê (layout de pastas)
  • Projeto ativo (projeto corrente e fase)

Princípio chave

CLAUDE.md é um índice de fatos, não documentação. Regras por área ficam em rules/. Referência técnica fica em kb/. CLAUDE.md aponta para eles.

Exemplo — Invariantes (workshop)

## Invariantes (nunca quebrar)
- Toda query a `negocio` é SOMENTE LEITURA
  (role RO + allowlist + LIMIT + timeout)
- App é runtime puro: nenhuma ingestão/carga
  em backend/. A ingestão vive só em seed/
- Stores pré-populados são sagrados: nunca
  `docker compose down -v` nem rm volumes
- Toda recomendação prescritiva amarrada a
  uma fonte recuperada

O hook de Stop detecta automaticamente quando a stack muda e avisa (nunca bloqueia). O /sync-context mostra o relatório de drift e pede confirmação antes de editar o CLAUDE.md — nada é reescrito às suas costas.

CONTEXT.md

Glossário puro de domínio

Criado e mantido pelo skill /grill-with-docs. Vive na raiz do projeto — não dentro de .claude/.

CLAUDE.md vs CONTEXT.md

CLAUDE.md Fatos técnicos do projeto: stack, comandos, invariantes, layout
CONTEXT.md Vocabulário de domínio: o que cada termo significa no negócio específico

Quando criar

Sempre que o projeto tem terminologia própria que pode ser confundida com significados genéricos. Rodado com um especialista de domínio presente na sessão de grill.

Exemplo (e-commerce)

# Glossário de domínio

## pedido
Intenção de compra confirmada pelo cliente.
Status: rascunho → aprovado → faturado.
NÃO confundir com `carrinho` (tentativa).

## sessão
Agregado diário de eventos de navegação
por cliente. Granularidade: dia+cliente.
Fonte: sessoes_diarias (schema negocio).

## meta
Alvo comercial por região/vendedor/período.
Unidade: R$ ou unidades, nunca %.
rules/

Regras path-scoped

Carregam SOMENTE quando o agente toca arquivos que casam com o padrão paths:. Regras sem paths: carregam em toda sessão.

Frontmatter de path-scope

---
paths:
  - backend/agent/**
  - backend/app/services/**
---

# Regra: Agente LangGraph

SQL allowlist: apenas SELECT.
Injete SET TRANSACTION READ ONLY.
LIMIT obrigatório em toda query.
statement_timeout = 5000ms.

Globais (sem paths:)

  • seguranca.md — SI sempre ativa
  • definicao-de-pronto.md — DoD sempre disponível

Exemplo real — rules/agente.md (workshop)

---
paths:
  - backend/agent/**
---

## SQL: somente leitura
- Toda query começa com:
  SET TRANSACTION READ ONLY;
- Allowlist de palavras: apenas SELECT,
  WITH, EXPLAIN, COUNT, AVG, SUM, MIN, MAX
- LIMIT injetado se ausente (máx 500)
- statement_timeout = '5s'
- Nunca INSERT/UPDATE/DELETE/DDL

## Qdrant
- Filtrar sempre por periodo_referencia
- Nunca filtrar por data_ingestao
settings.json

Permissões e gates automáticos

O que o agente pode fazer, o que está bloqueado, e o que roda automaticamente a cada Edit/Write ou ao parar.

allow — o que o agente pode

"allow": [
  "Bash(uv run pytest*)",
  "Bash(uv run ruff*)",
  "Bash(uv run mypy*)",
  "Bash(docker compose ps)",
  "Bash(git diff*)",
  "Bash(git log*)"
]

deny — o que está bloqueado

"deny": [
  "Bash(rm -rf*)",
  "Bash(docker volume rm*)",
  "Bash(docker compose down -v*)",
  "Bash(dropdb*)",
  "Bash(git push --force*)",
  "Write(seed/data/**)" ← dados sagrados
]

Hooks automáticos

"hooks": {
  // Ao editar: formata silenciosamente
  "PostToolUse": [{
    "matcher": "Edit|Write",
    "hooks": [{
      "type": "command",
      "command": "uv run ruff format . --quiet && uv run ruff check --fix --quiet"
    }]
  }],
  // Ao parar: gate completo
  "Stop": [{
    "hooks": [{
      "type": "command",
      "command": "uv run ruff check backend && uv run mypy backend && uv run pytest -q"
    }]
  }]
}
.mcp.json

Ferramentas externas

Servidor MCP define as ferramentas que o agente pode usar além do filesystem. O /harness-architect preenche com os valores reais do projeto.

Template (antes do harness-architect)

{
  "mcpServers": {
    "context7": {
      "command": "npx",
      "args": ["-y", "@upstash/context7-mcp"]
    },
    "postgres": {
      "command": "npx",
      "args": [
        "-y", "@modelcontextprotocol/server-postgres",
        "${POSTGRES_READONLY_URL}", ← placeholder
        "--access-mode=restricted"
      ]
    }
  }
}

O /harness-architect substitui ${POSTGRES_READONLY_URL} pela URL real extraída do .env — sem placeholder visível no arquivo final.

Context7 — docs oficiais em runtime

Permite que o agente busque documentação atual de qualquer lib — FastAPI, LangGraph, Qdrant, Airflow — diretamente durante a implementação. Sem hallucinar APIs desatualizadas.

Postgres — somente leitura

--access-mode=restricted bloqueia qualquer escrita no banco. O agente pode inspecionar schema, fazer SELECT, mas NUNCA INSERT/UPDATE/DELETE via MCP.

agents/

Especialistas de contexto fresco

Cada agente roda com contexto isolado — não carrega o histórico da sessão principal. Perfeito para revisões independentes e análises sem viés de recência.

Frontmatter obrigatório

---
name: revisor-codigo
description: >
  Revisor de código do time. Use após
  implementar / antes de commitar.
  Dispare com "revisa esse diff",
  "passa o revisor", "pronto pra commit?".
tools:
  - Read
  - Grep
  - Glob
  - Bash
color: purple
---

O que a description faz

É o único texto visto ao decidir qual agente despachar. Deve conter: nome do papel + quando usar + frases de gatilho. Sem isso, o agente nunca é escolhido automaticamente.

O que o revisor-codigo checa

  • Invariantes violados (somente-leitura, runtime puro, volumes sagrados)
  • Rules do path afetado (ex: SQL allowlist se tocou backend/agent/)
  • Critérios de aceite da task atendidos
  • Código desnecessariamente complexo ou duplicado
  • Ausência de teste para código novo

skills/

Procedimentos reutilizáveis

Skills são procedimentos multi-step que o agente executa quando invocados com /skill-name. Diferentes de commands: skills têm lógica, commands são curtos.

Tipos de skills

Workflow

Orquestram o fluxo: grill-me, to-prd, to-tasks, harness-architect, handoff. Instaladas no canônico por padrão.

Stack

Específicas de tecnologia: fastapi-templates, langgraph-fundamentals, pipeline-architect. Instaladas pelo /harness-architect conforme o tipo de projeto.

Utilitários

Comunidade/custom: caveman (comprime output), write-a-skill (cria novas skills), validar, scorecard.

Caveman — economizador de tokens

Comprime output do Claude para estilo conciso/primitivo. Útil em sessões longas quando contexto está ficando cheio. /caveman on → output comprimido. /caveman off → volta ao normal.

Estrutura de uma skill

skills/
  minha-skill/
    SKILL.md          ← instruções principais
    REFERENCE.md     ← referência técnica
    scripts/
      helper.sh      ← scripts de suporte

O SKILL.md contém as instruções passo-a-passo. O REFERENCE.md é opcional — carregado só quando a skill precisa de consulta técnica.

Criar nova skill

Use /write-a-skill para criar skills com estrutura correta, progressive disclosure e recursos embutidos. Não crie arquivos de skill à mão.

Instalação

skills-lock.json registra quais skills estão instaladas e suas versões. Funciona como um package.json para skills — garante reprodutibilidade entre clones.

commands/

Comandos invocáveis

Commands são curtos, diretos, sem processo multi-step. A diferença de uma skill está na complexidade — não no mecanismo.

/validar

Roda o gate manualmente: ruff check --fix + mypy + pytest -q. Mesmo gate do Stop hook, mas on-demand. Útil mid-task para checar antes de commitar.

/scorecard

Lê metrics/entregas.jsonl e exibe métricas de entrega: taxa de autonomia, mediana de tentativas no gate, distribuição de vereditos. Medição da qualidade do agente ao longo do tempo.

/novo-projeto

Orquestrador do fluxo guiado. Faz as 3 perguntas, cria STATUS.md e 00-ideia.md, e orienta qual skill chamar a seguir. É um command — curto, mas dispara todo o fluxo.

Command vs Skill — quando usar cada um

Command Menos de ~20 linhas. Executa uma coisa. Sem decisão de bifurcação. Ex: validar, scorecard.
Skill Procedimento multi-step. Pode ter lógica condicional. Pode chamar subagentes. Ex: grill-me, harness-architect.

Localização

Commands canônicos: .claude/commands/core/. Commands de projeto: .claude/commands/. A diferença é qual escopo eles cobrem — o core é universal, o projeto é específico.

rules/seguranca.md

A rule de SI que carrega sempre

Não tem paths: no frontmatter — carrega em toda sessão, independente do que está sendo editado. É a camada mais alta da hierarquia de rules.

O que a seguranca.md declara

  • Banco de dados de produção é somente leitura
  • PII nunca em logs ou outputs de debug
  • Secrets nunca hardcoded (sempre env var)
  • Operações destrutivas bloqueadas (rm -rf, dropdb, down -v)
  • LGPD declarada: base legal registrada antes de processar dados pessoais

Se houver conflito — SI ganha sempre

Hierarquia: SI rules > regras de domínio > regras de path. Nenhuma rule específica pode sobrescrever seguranca.md. Isso não é negociável.

SI vs nível do assessment

A seguranca.md define o piso mínimo. O nível SI do assessment (a/b/c/d) adiciona restrições sobre esse piso:

a Público — só o piso da seguranca.md
b Interno — + classificação de outputs
c Confidencial — + criptografia em repouso
d Restrito — requisitos vão para critérios de aceite obrigatórios nas tasks
