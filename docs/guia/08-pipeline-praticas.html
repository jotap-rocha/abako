SOLID

SOLID aplicado — cada princípio com código

Single Responsibility

  # só ingere

O

Open/Closed

class BaseTransform(ABC):
  @abstractmethod
  def transform(
    self, df
  ) -> DataFrame: ...

L

Liskov Substitution

def run_silver_layer(
  transform: BaseTransform,
  df: DataFrame
):
  # aceita qualquer
  # subclasse
  return transform.transform(df)

I

Interface Segregation

class Readable(Protocol):
  def read(self): ...

class Writable(Protocol):
  def write(self, df): ...

D

Dependency Inversion

Pipeline(
  reader,
  transform,
  writer,
  config
)
# depende de
# abstrações

Benefício central: Com SOLID, trocar o leitor (S3 → GCS), a camada (Bronze → Silver) ou o ambiente (local → Databricks) não exige reescrever lógica de negócio. Cada peça tem uma razão para mudar.

Config

Zero hardcode — 1 variável de ambiente troca tudo

PIPELINE_ENV=local → config/environments/local.yaml (Spark local, sem notificações)
PIPELINE_ENV=dev → config/environments/dev.yaml (Databricks DEV, notif ligadas)
PIPELINE_ENV=prd → config/environments/prd.yaml (Databricks PRD, threshold restrito) 
# Uso no código — sempre igual
config = PipelineConfig.from_env()

# Resolve tabela pelo ambiente
table = config.bronze_table("orders")
# dev  → dev_catalog.bronze.orders
# prd  → prd_catalog.bronze.orders
# local → orders

path = config.raw_path("orders/")
# dev  → /Volumes/dev_catalog/.../
# local → data/raw/orders/

O que PipelineConfig resolve

Zero condicional no pipeline: nunca if env == 'local' no código de transformação. Toda variação fica no config.

Portabilidade

O mesmo pipeline, ambientes diferentes

local.yaml — desenvolvimento

config = PipelineConfig.from_env()
# PIPELINE_ENV=local

path = config.raw_path("orders/")
# → "data/raw/orders/"

table = config.bronze_table("orders")
# → "orders"  (sem catalog)

dev.yaml — Unity Catalog

config = PipelineConfig.from_env()
# PIPELINE_ENV=dev

path = config.raw_path("orders/")
# → "/Volumes/dev_catalog/raw/..."

table = config.bronze_table("orders")
# → "dev_catalog.bronze.orders"

Mesmo código, saída diferente. O pipeline não sabe em que ambiente roda — só a config sabe. Isso garante que o comportamento em dev é idêntico ao de prd.

Unity Catalog

Unity Catalog — o catálogo que governa tudo

Namespace 3 níveis: {catalog}.{schema}.{table} = dev_catalog.bronze.orders

Regra inviolável: NUNCA execute código diretamente no workspace de PRD. Todo deploy via CI/CD (DABs). Acesso humano direto ao PRD = risco de incidente.

Benefícios do Unity Catalog

  • Lineagem automática entre tabelas e jobs

  • Column-level access control nativo

  • Data masking por coluna (PII)

  • Auditoria completa de acesso

  • Tags para governança e busca

CI/CD

Databricks Asset Bundles — infra como código

bundle:
  name: orders-pipeline

targets:
  dev:
    workspace:
      host: ${var.dev_workspace_url}
    variables:
      catalog: dev_catalog
  prd:
    workspace:
      host: ${var.prd_workspace_url}
    variables:
      catalog: prd_catalog

resources:
  jobs:
    orders_pipeline:
      name: orders_pipeline_${bundle.target}
      tasks:
        - task_key: bronze
          python_wheel_task:
            package_name: orders_pipeline
            entry_point: run_bronze

Comandos de deploy

# Validar antes de deployar
databricks bundle validate

# Deploy para DEV
databricks bundle deploy --target dev

# Deploy para PRD (apenas CI/CD)
databricks bundle deploy --target prd

# Rodar job imediatamente
databricks bundle run --target dev \
  orders_pipeline

CI/CD: GitHub Actions faz o deploy no merge para main. Nenhum humano precisa rodar o deploy manualmente em PRD.

Jobs, clusters, notebooks, DLT pipelines, permissões, schemas, secrets — tudo versionado em YAML.

On-premises

Airflow — obrigatório em on-premises

Regra: em ambientes on-premises, Airflow é obrigatório para scheduling. Nenhum cron job manual. Sem Airflow = sem governança de execução.

Medallion DAG

with DAG(
    "orders_pipeline",
    schedule="@daily",
    default_args={"retries": 2}
) as dag:

    bronze = PythonOperator(
        task_id="bronze",
        python_callable=run_bronze,
        op_kwargs={
          "config": PipelineConfig.from_env()
        }
    )
    silver = PythonOperator(
        task_id="silver", ...)
    gold = PythonOperator(
        task_id="gold", ...)

    bronze >> silver >> gold

PipelineConfig via op_kwargs

Injete PipelineConfig.from_env() via op_kwargs — nunca como variável global do DAG. Isso permite que workers Airflow rodem com diferentes PIPELINE_ENV sem interferência.

Boas práticas no DAG

  • retries: 2 por task (mínimo em produção)

  • retry_delay: 5 minutos entre tentativas

  • on_failure_callback: notificação no Slack

  • execution_timeout: defina sempre — evita tasks zumbi

  • catchup=False: não reprocessar histórico por padrão

dag_id único e descritivo: use {fonte}_{pipeline}_{frequência}. Ex: erp_orders_daily

Checklist

Antes de ir a produção — 12 itens

✅ Configuração externalizada (zero hardcode no código Python)

✅ Lineage columns em todas as camadas (Bronze, Silver, Gold)

✅ Raw imutável — nunca sobrescrito nem deletado

✅ Quarantine table criada e testada com dados reais

✅ Contract YAML versionado e validado no pipeline

✅ Schema evolution strategy configurada por ambiente

✅ Structured logging com todos os campos obrigatórios

✅ Nenhum PII em logs — auditado e confirmado

✅ Alertas de quarantine rate configurados e testados

✅ Airflow DAG (on-prem) ou Databricks Job (cloud) configurado

✅ DABs bundle.yml com targets dev e prd separados

✅ Testes unitários para cada transformer (pytest + local Spark)
