Multi-Tenant

Isolamento, RLS, JWT e vector isolation

Modelos de Isolamento RLS JWT Vector Isolation Invariantes

"Isolamento multi-tenant não é uma feature — é um invariante. Qualquer query que não carregar tenant_id como primeiro predicado é um bug de segurança."

Risco Crítico

O problema: vazamento entre tenants

O que pode dar errado

  • Query sem tenant_id — retorna dados de todos os tenants
  • Body forjado — cliente envia tenant_id de outro tenant
  • Semântica vetorial sem pre-filter — documentos de tenants diferentes competem na busca
  • RLS desligado — política existe mas não está ativa na tabela

Diagrama: sem isolamento

Tenant A → App / Query → sem WHERE tenant_id
↓
Dados do Tenant A + Dados do Tenant B → vê dados Tenant B

Falha crítica de segurança — vazamento de dados entre clientes.

Impacto real

Um único endpoint sem isolamento adequado pode expor dados de todos os tenants da plataforma. LGPD, GDPR e contratos com clientes podem ser violados em uma única requisição mal-formada.

Arquitetura

Modelos de Isolamento

class TenantRepo:

        self, tenant_id: str

            "SET app.tenant_id=$1",

Schema Separation

# Schema por tenant
def get_schema(tenant_id):
    return f"tenant_{tenant_id}"

async def query(tenant_id, sql):
    schema = get_schema(tenant_id)
    await conn.execute(
        f"SET search_path={schema}"
    )
    return await conn.fetch(sql)

Postgres

RLS multi-tenant — setup completo

-- 1. Tabelas base
CREATE TABLE tenants (
    id   UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    slug TEXT NOT NULL UNIQUE,
    plan TEXT NOT NULL DEFAULT 'starter'
);

CREATE TABLE casos (
    id        UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id UUID NOT NULL REFERENCES tenants(id),
    titulo    TEXT NOT NULL,
    status    TEXT NOT NULL DEFAULT 'aberto',
    created_at TIMESTAMPTZ DEFAULT now()
);

-- 2. Role helper — extrai tenant do JWT
CREATE OR REPLACE FUNCTION current_tenant_id()
RETURNS UUID AS $$
  SELECT current_setting('app.tenant_id')::UUID
$$ LANGUAGE sql STABLE;

-- 3. Ativar RLS
ALTER TABLE casos ENABLE ROW LEVEL SECURITY;
ALTER TABLE casos FORCE ROW LEVEL SECURITY;
-- 4. Políticas para todas as operações
CREATE POLICY casos_select ON casos
  FOR SELECT USING (
    tenant_id = current_tenant_id()
  );

CREATE POLICY casos_insert ON casos
  FOR INSERT WITH CHECK (
    tenant_id = current_tenant_id()
  );

CREATE POLICY casos_update ON casos
  FOR UPDATE
  USING     (tenant_id = current_tenant_id())
  WITH CHECK (tenant_id = current_tenant_id());

CREATE POLICY casos_delete ON casos
  FOR DELETE USING (
    tenant_id = current_tenant_id()
  );

-- 5. Verificação
SELECT schemaname, tablename, rowsecurity
FROM pg_tables
WHERE tablename = 'casos';
-- rowsecurity deve ser: t

FORCE ROW LEVEL SECURITY garante que nem o owner da tabela burla as policies — sem exceções silenciosas.

Anti-padrão

tenant_id do JWT, nunca do body

Anti-padrão: body forjavel

# NUNCA FACA ISSO
class CasoRequest(BaseModel):
    titulo: str
    tenant_id: str  # ← forjavel!

@router.post("/casos")
async def criar_caso(body: CasoRequest):
    # cliente envia qualquer tenant_id
    await db.insert(
        tenant_id=body.tenant_id,  # ← BUG
        titulo=body.titulo
    )

Qualquer cliente pode inserir dados em qualquer tenant apenas alterando o JSON body.

Correto: tenant_id do JWT verificado

from contextvars import ContextVar
from fastapi import Depends, HTTPException
import jwt

_tenant_ctx: ContextVar[str] = ContextVar("tenant_id")

async def get_tenant_id(
    authorization: str = Header(...)
) -> str:
    try:
        token = authorization.split(" ")[1]
        payload = jwt.decode(
            token,
            settings.JWT_SECRET,
            algorithms=["HS256"]
        )
        tenant_id = payload["tenant_id"]
        _tenant_ctx.set(tenant_id)
        return tenant_id
    except Exception:
        raise HTTPException(401)

# Uso no endpoint — tenant_id do JWT
@router.post("/casos")
async def criar_caso(
    body: CasoRequest,
    tenant_id: str = Depends(get_tenant_id)
):
    await db.set_tenant(tenant_id)
    return await db.insert_caso(body.titulo)
Performance + Segurança

tenant_id como primeiro predicado

Errado — ordem incorreta

-- status primeiro: ignora o índice de tenant
SELECT * FROM casos
WHERE status = $1          -- ← predicado amplo
  AND tenant_id = $2;      -- ← chega tarde

-- Resultado: Seq Scan ou Index Scan ineficiente
-- Pode vazar via race condition em RLS

O planner pode optar por um scan amplo antes de aplicar o filtro de tenant — cenário de data leak em edge cases.

Correto — tenant_id primeiro

-- tenant_id SEMPRE primeiro
SELECT * FROM casos
WHERE tenant_id = $1        -- ← filtra o universo
  AND status = $2           -- ← refina dentro do tenant
ORDER BY created_at DESC
LIMIT 50;

-- Índices obrigatórios
CREATE INDEX ON casos (tenant_id, status);
CREATE INDEX ON casos (tenant_id, created_at DESC);

-- Verificar com EXPLAIN ANALYZE
EXPLAIN ANALYZE
SELECT * FROM casos
WHERE tenant_id = 'uuid-aqui'
  AND status = 'aberto';

Por que a ordem importa no índice composto

Um índice (tenant_id, status) permite um Index Scan direto com WHERE tenant_id=$1 AND status=$2. Invertido — (status, tenant_id) — resulta em Index Scan em todos os tenants para aquele status, depois filtra. Com 1000 tenants, a diferença é de 1000x no volume lido.

Vector Isolation

Isolamento vetorial

Por que semântica não garante isolamento

Dois documentos de tenants diferentes podem ser semanticamente idênticos (ex.: mesma cláusula contratual, mesmo script de atendimento). O vetor de embeddings será quase igual — sem pre-filter, o tenant A recebe documentos do tenant B nos top-k resultados.

Anti-padrão: filtrar pos-busca

# NUNCA FACA ISSO
results = qdrant.search(
    collection_name="docs",
    query_vector=embedding,
    limit=20
)
# filtrar aqui ja e tarde demais
filtered = [
    r for r in results
    if r.payload["tenant_id"] == tenant_id
]
# top-k pode ter 0 resultados uteis
# e ainda vaza metadados via scores

Correto: pre-filter obrigatorio

from qdrant_client.models import (
    Filter, FieldCondition, MatchValue
)

# Qdrant: pre-filter ANTES do semantico
results = qdrant.search(
    collection_name="docs",
    query_vector=embedding,
    query_filter=Filter(must=[
        FieldCondition(
            key="tenant_id",
            match=MatchValue(value=tenant_id)
        )
    ]),
    limit=10
)

# pgvector: tenant_id no WHERE
SELECT id, content,
       embedding <=> $1 AS dist
FROM documentos
WHERE tenant_id = $2   -- pre-filter
ORDER BY dist
LIMIT 10;
Revisão de PR

Checklist antes de qualquer PR que toque dados de tenant

Banco de dados

  • Nova tabela tem tenant_id UUID NOT NULL
  • ENABLE ROW LEVEL SECURITY na tabela
  • FORCE ROW LEVEL SECURITY também ativo
  • Policy para SELECT com USING
  • Policy para INSERT com WITH CHECK
  • Policy para UPDATE com USING + WITH CHECK
  • Policy para DELETE com USING

Índices e queries

  • Índice composto (tenant_id, ...) criado
  • tenant_id é o primeiro predicado em toda query
  • EXPLAIN ANALYZE confirma Index Scan
  • tenant_id extraído do JWT (não do body)

Busca vetorial

  • Qdrant: Filter(must=[FieldCondition(...)]) no search
  • pgvector: WHERE tenant_id=$1 antes do ORDER BY dist
  • Nenhum filtro pos-busca — pre-filter obrigatório

Regra de ouro

Se qualquer item deste checklist estiver desmarcado, o PR não passa para revisao. Isolamento multi-tenant não tem "parcialmente implementado".

Invariantes

Os 5 invariantes multi-tenant

ID Invariante Proíbe Consequência de violar
MT-01 tenant_id é o primeiro predicado em toda query WHERE sem tenant_id ou tenant_id não como primeiro filtro Cross-tenant data leak, table scan em todos os tenants
MT-02 RLS ativo em toda tabela com dados de tenant Tabela sem ENABLE + FORCE ROW LEVEL SECURITY Qualquer query sem SET retorna dados de todos os tenants
MT-03 Busca vetorial usa pre-filter de tenant_id Filtro pos-busca ou ausência de filtro no search Documentos de outros tenants nos top-k, vazamento semântico
MT-04 tenant_id sempre extraído do JWT verificado tenant_id vindo do body, query param ou header não verificado Tenant impersonation — cliente acessa dados de qualquer tenant
MT-05 Índice composto obrigatório em tabela com >10k rows Query sem índice adequado em tabela de tenant grande Seq scan custoso, potencial timeout, DoS por tenant malicioso

Estes invariantes são verificados pelo revisor-codigo antes de todo PR. Violação de qualquer MT-XX = PR bloqueado.
