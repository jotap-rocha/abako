Orientação

"Onde estou?" — 4 fontes de verdade

Cada fonte responde uma pergunta diferente. Ler as 4 juntas dá contexto completo em menos de 2 minutos.

📍

Em qual fase está o projeto?

.claude/projetos/{slug}/STATUS.md

Fase atual (ideia → ship), nível SI, checklist de 7 fases. Atualizado por cada agente harness-* ao encerrar.

📋

Quais tasks e em que status?

tasks/README.md

Índice de todas as tasks com status (not-started / in-progress / done) e blockers. Gerado e atualizado pelo harness-build.

🔄

O que foi feito na última sessão?

HANDOFF.md

Memória entre sessões. O que foi feito, decisões tomadas, próximo passo imediato. Escrito antes de encerrar uma sessão longa.

📊

Qual foi a qualidade das entregas?

metrics/entregas.jsonl

Histórico mensurável. Uma linha JSON por task fechada. Alimenta o /scorecard com taxa de autonomia, gate attempts, vereditos.

Cada agente harness-* atualiza o STATUS.md ao encerrar — checando a fase concluída e apontando a próxima. Não requer edição manual.

tasks/README.md

O board de tasks

Criado pelo /to-tasks. Atualizado pelo harness-build à medida que cada task avança. Visão consolidada de todo o backlog.

Exemplo — tasks/README.md

Cada task tem seu próprio arquivo

tasks/task-01-get-produtos.md contém: o que construir, critérios de aceite, contexto técnico, log de tentativas do gate.

Blockers são respeitados

O harness-build lê os blockers antes de iniciar. Se a task-04 tem "blocked by: task-03" e task-03 não está done, a task-04 é pulada automaticamente.

HANDOFF.md

Memória entre sessões

Criado pelo skill /handoff — executado manualmente antes de encerrar uma sessão longa. Vive na raiz do projeto.

Template do HANDOFF.md

# HANDOFF — 2026-06-27

## O que foi feito nessa sessão
- task-01 concluída e comitada
- task-02 concluída: filtros por categoria
  e região com LIMIT 500 + somente leitura
- task-03 iniciada: Qdrant client conectado,
  mas busca semântica ainda não testada

## Decisões tomadas
- Escolhemos cosine distance para Qdrant
  (ADR-0002 registrado)
- Timeout de Qdrant: 3s (ajustável por env)

## Próximo passo imediato
Finalizar task-03: testar busca semântica
com golden dataset em seed/evals/golden/

## Estado das tasks
01 ✓ | 02 ✓ | 03 🔄 | 04 ○ | 05 ○

Como usar na próxima sessão

Na primeira mensagem da nova sessão, Claude lê o HANDOFF.md e retoma de onde parou — sem precisar reexplicar o contexto. O STATUS.md confirma a fase, o HANDOFF.md confirma o momento exato.

Quando rodar /handoff

  • Antes de encerrar uma sessão com mais de 1h de trabalho
  • Antes de uma pausa de mais de um dia
  • Quando está no meio de uma task não concluída
  • Quando tomou uma decisão técnica relevante

O HANDOFF.md não substitui commits e ADRs — é memória de curtíssimo prazo, não documentação permanente. Pode ser sobrescrito a cada sessão.

Aviso de Goodhart

O gate é um alvo legítimo — testes reais. Métricas de humano (taxa de aprovação do revisor, intervenções) não são para o agente otimizar — são lagging indicators para o time melhorar o harness.

docs/adr/

Decisões que precisam de memória

ADR = Architecture Decision Record. Escrito quando uma decisão técnica é contestável — não é burocracia, é contexto para o próximo desenvolvedor (ou para você daqui a 3 meses).

Quando escrever um ADR

  • Decisão técnica com pelo menos 2 alternativas consideradas
  • Decisão que alguém razoável poderia questionar
  • Decisão que teria custo significativo de reversão
  • Quando a Definição de Pronto exige (DoD item 5)

Formato simples

# ADR-0001: LangGraph Determinístico

## Contexto
Precisamos de um grafo de agente que
seja auditável e testável. ReAct livre
é difícil de testar deterministicamente.

## Decisão
Usar LangGraph com grafo determinístico:
LLM decide DENTRO dos nós, não controla
o fluxo. search é tool única parametrizada.

## Alternativas consideradas
- ReAct livre (descartado: não auditável)
- LangChain chain (descartado: sem estado)

## Consequências
+ Testável, auditável, reprodutível
- Menos flexível para casos edge

Quando é criado vs arquivado

Durante build O desenvolvedor/agente escreve o ADR no momento da decisão — contexto fresco, alternativas ainda na cabeça.
No ship O harness-ship lista todos os ADRs criados na retro (05-retro.md) — servem como histórico da evolução da arquitetura.

Naming convention

docs/adr/ADR-NNNN-descricao-kebab-case.md
Numeração sequencial. Nunca deleta um ADR — se a decisão mudou, escreve um novo que a supersede.

ADR não é documentação de código. É memória organizacional. O código documenta o quê; o ADR documenta o porquê de ter chegado nesse quê.

Auto-geração

Ferramentas que escrevem documentação

O harness privilegia geração automática sobre edição manual — documentação que não é gerada automaticamente tende a ficar desatualizada.

Ferramenta O que cria Quando usar Manual ou auto?
/readme-maker README.md do projeto Ao final de uma feature ou no ship Manual
/sync-context Atualiza CLAUDE.md, CONTEXT.md e AGENTS.md Obrigatório no fechamento (ship / EXIT_COMPLETE do Dev Loop) Semi-auto
/grill-with-docs CONTEXT.md (glossário) Com especialista de domínio presente Manual
harness-ship 05-retro.md (retrospectiva) Automático ao encerrar o projeto Auto
harness-build metrics/entregas.jsonl Automático ao fechar cada task Auto
/handoff HANDOFF.md Antes de encerrar sessão longa Manual
Dev / agente docs/adr/ADR-NNNN.md Durante o build, a cada decisão contestável Manual

A regra de ouro: se um documento pode ser gerado automaticamente, ele deve ser. Documentação manual só quando o contexto humano é insubstituível (ADRs, glossário de domínio, handoff).
