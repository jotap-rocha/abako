Por que desde o dia 1

O risco real de um agente sem guardrails

🔥 LLM escreve DROP TABLE clientes ao refatorar queries — "simplifiquei a estrutura do banco"
🔥 docker compose down -v ao "limpar o ambiente" — apaga 5 anos de dados + indices do Qdrant
🔥 rm -rf seed/data/ ao "remover arquivos temporarios" — perde datasets de producao irrecuperaveis
🔥 PII de usuario aparece em log de debug que vai para o Datadog — violacao LGPD detectada semanas depois
🔥 Secret de producao hardcoded no codigo que vai para o GitHub — rotacao de emergencia, post-mortem, cliente impactado

Nao e paranoia. Esses acidentes acontecem. O harness previne com deny list, rules e SI assessment obrigatorio desde o /novo-projeto.

Vetores de risco

4 vetores de risco do LLM como agente

🗑

1 — Destruicao de dados

DROP TABLE, DELETE sem WHERE, docker volume rm, rm -rf em dados importantes. O agente pode destruir anos de dados em segundos — sem intenção maliciosa, apenas seguindo instrucoes vagas.

👁

2 — Exposicao de PII

CPF, email, nome, dados financeiros em logs, outputs brutos, URLs de debug. PII que aparece em qualquer canal externo (Datadog, Langfuse, GitHub Issues) e violacao LGPD imediata.

✋

3 — Escrita nao-autorizada em producao

UPDATE em banco de producao sem aprovacao humana. O agente pode "corrigir dados" diretamente — sem revisao, sem rollback, sem audit trail adequado.

🔁

4 — Vazamento cross-tenant

Em sistemas multi-empresa, dados do cliente A acessiveis ao cliente B. Sem RLS e filtro por company_id no JWT, uma query errada expoe dados de todos os tenants.

LGPD

O que e dado pessoal e como o agente trata

Dados pessoais (LGPD Art. 5)

CPF Email Nome completo Localizacao Biometria Dados de saude Dados financeiros IP + device

Principios LGPD relevantes

  • Finalidade: propósito declarado no CLAUDE.md antes de qualquer dado pessoal
  • Minimizacao: agente acessa so o necessario para a tarefa
  • Transparencia: audit log de toda operacao que toca PII

O agente NUNCA faz com PII

  • ✗ Logar sem mascaramento
  • ✗ Exibir em output bruto
  • ✗ Expor em URL query string
  • ✗ Passar para LLM externo sem consentimento
  • ✗ Incluir em mensagem de erro devolvida ao frontend

Guardrail

Deny list — o que o agente nunca executa

"deny": [
  "Bash(rm -rf:*)",
  "Bash(docker compose down -v:*)",
  "Bash(docker compose down --volumes:*)",
  "Bash(docker volume rm:*)",
  "Bash(docker volume prune:*)",
  "Bash(dropdb:*)",
  "Bash(mysqladmin drop:*)",
  "Bash(databricks workspace delete:*)",
  "Bash(git push --force:*)",
  "Bash(git reset --hard:*)"
]

Como funciona

O agente tenta executar o comando e recebe um erro de permissao. Nao consegue prosseguir. O usuario deve explicitamente aprovar ou usar uma abordagem diferente.

Por que esses especificamente

  • rm -rf: risco de apagar dados de seed/Qdrant/MinIO
  • docker volumes: apaga dados persistentes (5 anos de dados)
  • dropdb: destruicao irreversivel do banco
  • git push --force: reescreve historico no remoto
  • git reset --hard: descarta commits locais sem aviso

O deny list esta em .claude/settings.json no canonico e e herdado por todos os projetos criados a partir dele.

Rule global

rules/seguranca.md — carrega SEMPRE

Banco de producao = somente leitura

Role RO para o agente. Nenhum INSERT / UPDATE / DELETE sem aprovacao humana explicita e ADR registrado.

PII: nunca logar, nunca exibir sem mascaramento

Qualquer campo que possa identificar uma pessoa passa por mascaramento antes de logar, exibir, ou retornar em response.

Secrets: nunca hardcoded

Sempre via .env. O agente recusa inlinear qualquer valor que pareca senha, token, key ou connection string no codigo.

LGPD: propósito declarado no CLAUDE.md

Antes de qualquer operacao com dado pessoal, o propósito deve estar no CLAUDE.md. Sem declaracao de finalidade, o agente recusa prosseguir.

Sem paths: — carrega sempre

Ao contrario das rules de stack (backend.md, pipeline.md), a seguranca.md nao tem restricao de path. E carregada em toda sessao, independente do arquivo aberto.

Antes de qualquer SQL de escrita

A rule exige: confirmar com o usuario, criar ADR em docs/adr/, e gravar no audit log. Sem esses tres passos, o agente bloqueia a operacao.

"Esta rule nao tem excecao."

Portao de entrada

SI como portao de entrada, nao afterthought

Pergunta obrigatoria no /novo-projeto

"Esse projeto lida com dados sensiveis?
  a) Nao — apenas dados abertos ou sinteticos
  b) Sim — dados de usuarios mas nao PII direto
  c) Sim — PII (CPF, email, dados financeiros/medicos)
  d) Sim — banco de producao com risco de escrita"
Nivel a Dados abertos ou sinteticos

SI rules padrao ja presentes no canonico. Sem configuracao extra.

Nivel b Dados de usuarios sem PII

Adiciona deny list de banco na allowlist. Exemplo: workshop (dados de sessao sinteticos).

Nivel c PII (CPF, email, financeiro)

Adiciona rule de PII masking + [AVISO_LGPD] no CLAUDE.md com propósito declarado.

Nivel d Banco de producao com escrita

Deny list extendida + ADR obrigatorio antes de qualquer operacao de escrita.

Dupla camada

Client-side + database-side

Client-side (harness)

  • ✓ Allowlist de comandos SQL no settings.json (apenas SELECT)
  • ✓ Deny list de operacoes destrutivas (rm, docker volumes, dropdb)
  • ✓ Rule: confirmar com usuario antes de qualquer escrita
  • ✓ Hook PostToolUse: ruff check em todo arquivo Python modificado
+

Database-side (infra)

  • ✓ Role somente leitura para o agente (agente_ro)
  • ✓ SET TRANSACTION READ ONLY injetado em todo SQL
  • ✓ statement_timeout = 5s — mata queries longas
  • ✓ RLS (Row Level Security) em multi-tenant — filtra por company_id do JWT

Exemplo real do workshop

A tool run_sql injeta ambas as camadas antes de executar: client-side valida que e SELECT, database-side forca READ ONLY + timeout. O LLM nunca executa SQL diretamente.

Exemplos reais

Workshop vs SisFraude — lado a lado

Dimensao Workshop (agente de vendas) SisFraude (fraud detection)
SI Assessment Nivel b dados de sessao, nao PII Nivel c+d CPF, dados financeiros, banco PRD
Invariante principal negocio somente leitura + LIMIT + timeout RLS por company_id (JWT) + CPF masking
Deny critico docker volumes (5 anos de dados Qdrant) DELETE restrito a manager/admin apenas
PII handling N/A (dados sinteticos) maskCPF() + maskEmail() em toda exibicao
Audit log metrics/entregas.jsonl (runs do agente) history_events (imutavel, INSERT-only, nunca UPDATE)

Workshop usa o minimo de SI necessario porque os dados sao sinteticos — mas a deny list e as rules continuam ativas para proteger os volumes do Qdrant.

SisFraude usa o nivel maximo: RLS, mascaramento, audit log imutavel, e ADR obrigatorio para qualquer escrita em producao.
