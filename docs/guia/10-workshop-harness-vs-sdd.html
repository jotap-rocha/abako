Módulo 1 · Os 3 Modos de Falha

Por que IA sem estrutura falha

🧹

Blank Slate

Toda sessão recomeça do zero. O agente não sabe quem é você, qual é o produto, quais são os invariantes. Você re-explica tudo.

Custo: 15-30 min por sessão desperdiçados.

🔇

Session Amnesia

Decisões de arquitetura, invariantes de produto, regras de SI — tudo se perde ao fechar o chat. O agente repete erros já corrigidos.

Custo: bugs recorrentes, inconsistência.

💥

No Gates

A IA comita código que não passa no type check, não tem teste, ou viola regras de SI. Você descobre em produção ou na PR review.

Custo: retrabalho, incidentes, perda de confiança.

A raiz do problema: o modelo é capaz — o que falta é o ambiente que o governa. Harness é esse ambiente.

Módulo 3 · Spec Driven Development

SDD: 5 fases, artefatos persistidos

01
/brainstormExploração livre da ideia → BRAINSTORM_{F}.md
02
/defineCaptura de requisitos → DEFINE_{F}.md
03
/designArquitetura técnica → DESIGN_{F}.md
04
/buildImplementação → BUILD_REPORT_{F}.md
05
/shipEntrega → SHIPPED_{date}.md

O que o SDD resolve bem

  • Disciplina de faseamento — impede o "só sai codando"
  • Artefatos persistidos por feature
  • Agentes especializados por fase
  • Workflow reproduzível entre projetos

Criado pelo agentspec

Framework de desenvolvimento guiado por agentes — base sobre a qual o harness method foi construído.

Módulo 3 · Pontos Cegos do SDD

O que o SDD não cobre

  • Sem SI assessment — segurança e privacidade não são first-class (sem níveis a/b/c/d)
  • Sem detecção de tipo — pipeline ≠ webapp ≠ API. O grill é genérico para todos.
  • Sem gates obrigatórios — ruff + mypy + pytest existem, mas não são enforced por agente
  • Sem /scorecard — não há métricas de entrega, autonomia ou taxa de revisão
  • Sem multi-projeto — um STATUS.md global, não um por slug de projeto
  • Sem deny list executável — não bloqueia rm -rf nem git push --force a nível de hook

Quando SDD é suficiente

  • Experimento rápido < 1 semana
  • Projeto solo, sem PII
  • Sem dados de produção
  • Sem time compartilhando o mesmo repo

"SDD é o DNA.
O harness é o organismo adulto."

Módulo 4 · O Caminho de Upgrade

SDD → Harness é aditivo, não substituição

Use SDD quando...

  • Experimento rápido < 1 semana
  • Trabalho solo, sem PII
  • Sem dados de produção envolvidos
  • Sem time compartilhando o repo

Use Harness quando...

  • Time (2+ devs compartilhando o repo)
  • PII ou dados de produção envolvidos
  • Multi-sessão (projeto > 1 dia)
  • Pipeline de dados ou agente LLM
Claude Code

Cursor

.cursorrules + Cursor Rules (beta) — texto interpretado pelo modelo. Sugestões, não enforcement executável.

Gap crítico: Claude Code executa hooks em shell. Cursor lê regras como texto. Harness é enforcement real.

Path-scoped rules

rules/pipeline.md só carrega ao tocar src/pipeline/**. Contexto relevante, sem poluição.

Módulo 5 · CLAUDE.md vs .cursorrules

Como cada ferramenta persiste contexto

Claude Code — CLAUDE.md
  • Carregado em toda sessão automaticamente
  • Suporta seções declarativas: Stack, Comandos, Invariantes, KB Map
  • Complementado por rules/ path-scoped (carregam só ao tocar aquele path)
  • CONTEXT.md separado para glossário de domínio
  • .claude/projetos/ persiste estado por projeto
Cursor — .cursorrules
  • Carregado na maioria das sessões
  • Texto plano — sem seções estruturadas
  • Cursor Rules (Beta): regras por file glob — similar ao path-scoped, mas menos maduro
  • Sem equivalente nativo de STATUS.md ou HANDOFF
  • Memória via notas manuais ou ferramentas externas

Diferença fundamental: CLAUDE.md é o índice de fatos duráveis. rules/ são os invariantes executáveis. Juntos, eliminam os 3 modos de falha do Módulo 1.

Módulo 5 · Claude Tips — Nível Iniciante

Hacks que previnem 80% das sessões desperdiçadas

Baseado em @sairahul1 · 2.9M views · "27 Hidden Claude Features"

Memory persistence ritual

Harness: toda sessão começa com cat STATUS.md. Termina com /handoff. Novo agente retoma exatamente do ponto certo.

Cursor: você faz isso manualmente em notas ou README.

Custom instructions = invariantes reais

CLAUDE.md não é um README — é o sistema imunológico. Escreva invariantes do produto, não tutoriais.

Concurrent projects sem interferência

Harness: múltiplos slugs em .claude/projetos/. agente-de-vendas + fraud-detector + data-lake — cada um com STATUS.md próprio.

Cursor: sem equivalente nativo — você gerencia mentalmente.

Start ritual

Toda sessão: 1) leia STATUS.md, 2) leia tasks/README.md, 3) abra o HANDOFF.md da última sessão. Nunca re-explique contexto.

SI levels — o que significa cada um

a — público, sem restrições

b — dados internos, uso dos usuários

c — PII direto (CPF, email, saúde)

d — produção crítica, dados restritos

Por que o tipo importa

Tipo pipeline → /grill-me faz +10 perguntas obrigatórias (volume, SLA, lineage, quarantine…). Tipo agente LLM → perguntas sobre grounding e determinismo.

Agentes, Skills e KBs

O que você vai ganhar

Módulo 7 · Agente vs Skill vs KB

A decisão mais importante do harness

Agente

Contexto fresco · especialista · caro

Use quando precisa de isolamento e expertise de domínio.

Exemplos:

revisor-codigo · kb-architect · harness-build · rag-architect

Skill

Playbook de procedimento · barato · reutilizável

Use para procedimentos que você repete. Roda no contexto atual.

Exemplos:

grill-me · to-prd · validar · gen-tests · new-adr

Knowledge Base

Documentação de domínio · persistida · consultada

Consumida por agentes e skills. Fica em .claude/kb/.

Exemplos:

kb/fastapi/ · kb/pipeline/ · kb/langgraph/ · kb/rag/

Árvore de decisão: "Precisa de contexto limpo + expertise?" → Agente. "É um procedimento que repito?" → Skill. "É documentação de referência?" → KB.

Claude Code

Agents em .claude/agents/*.md com tool restrictions declaradas. Skills em .claude/skills/*/SKILL.md.

Cursor

Composer Agents — contexto fresco similar. Sem arquivos de definição estruturados. Sem equivalente de Skill ou KB.

Módulo 7 · Context-7 MCP

Docs vivos — nunca use documentação do training data

O problema

Docs de bibliotecas no training data ficam velhas. O LLM hallucina a API certa, usa parâmetros depreciados, sugere padrões de versões antigas.

Context-7 MCP resolve

MCP server que busca docs oficiais em tempo real:

  • resolve-library-id → "fastapi" para /tiangolo/fastapi
  • get-library-docs → ID + tópico + versão → docs atuais

Score de confiança do kb-architect

Doc < 1 mês: +0.05 confiança

Doc > 6 meses: −0.05 confiança

Breaking change detectada: −0.15 confiança

Exemplos de produção: +0.05 confiança

Claude Code

Context-7 MCP → docs no contexto do agente automaticamente via .mcp.json.

Cursor

@docs feature → indexa URLs específicas. Menos automatizado, sem scoring de frescor.

Segurança da Informação desde o Dia 0

Módulo 8 · Os 4 Vetores de Risco

O que pode dar errado sem SI no harness

💣 Destruição

rm -rf · docker volume rm · dropdb · DELETE em produção sem ADR

Bloqueados via settings.json deny list — hook shell, não instrução de texto.

👁 Exposição de PII

CPF, email, nome, IP, saúde em logs, URLs ou output do LLM. LGPD: dados pessoais identificam ou podem identificar uma pessoa.

Regra: PII nunca em logs. Sempre mascarado na UI.

✍️ Escrita não autorizada em produção

DELETE/DROP sem ADR aprovado por humano. Banco de produção é somente leitura por padrão — role RO, LIMIT, timeout declarados em CLAUDE.md.

🔗 Vazamento cross-tenant

Query de tenant A retorna dados de tenant B. RLS obrigatório em toda query multi-tenant. Filtro de tenant no nível do banco, não da aplicação.

SI levels: a=público · b=interno/uso de usuários · c=PII direto · d=produção crítica/dados restritos

Módulo 9 · /scorecard e ADRs

Meça o que importa — não o que é fácil

/scorecard calcula de metrics/entregas.jsonl

Autonomia %tasks fechadas sem edição humana
Gate attemptsrodadas de /validar até passar
Aprovação revisortaxa de aprovação first-try
Bloqueiostasks reabertas ou bugs pós-ship

Não persiga vaidade (linhas de código, commits). A meta é: autonomia % subindo ao longo dos projetos.

ADRs — Architecture Decision Records

Quando criar um ADR:

  • Escolha de tecnologia ou biblioteca
  • Decisão de segurança (escopo de escrita)
  • Breaking change de schema
  • Qualquer decisão que você vai questionar em 3 meses

Formato: data · contexto · decisão · consequências · alternativas consideradas. Um arquivo por decisão em docs/adr/ADR-NNNN.md.

Módulo 10 ⏱ 15 min · lecture

Pipeline Specialization

Módulo 10 · Medallion no Harness

Arquitetura Medallion com regras aplicadas

Raw (sagrado/imutável)

Nunca transformado, nunca deletado. Ponto de auditoria.

Bronze (tipagem + metadata)

Colunas obrigatórias: _ingested_at · _source · _run_id · _batch_id

Silver (limpeza + validação)

Contratos ODCS aplicados. Quarantine table para dados rejeitados.

Gold (agregações prontas)

Consumível por BI, ML, API. SLA de freshness aplicado aqui.

Quarantine — nunca delete dados ruins

Registre _quarantine_reason · _quarantine_ts · _run_id. Audite. Corrija a source. Reprocesse.

Zero hardcode de ambiente

PIPELINE_ENV=dev → config/environments/dev.yaml → resolve dev_catalog.bronze.orders. Nunca escreva catalog name no código.

Agentes gerados pelo /harness-architect

Para pipelines: pipeline-architect · schema-guardian · rules de pipeline e schema evolution são criadas automaticamente.

Módulo 11 ⏱ 30 min · hands-on em grupos

Capstone Exercise

O que você vai ganhar

Você vai aplicar o método completo num projeto real do seu contexto — e terminar o workshop com STATUS.md, grill e PRD prontos para usar amanhã.

✋ Capstone · 25 min

Crie seu projeto com o método completo

✋ Capstone — Em grupos de 2-3 pessoas. Facilitador circula.
  1. Escolham um projeto real ou realista do contexto de vocês (não um todo-list).
  2. Execute /novo-projeto → responda as 3 perguntas: ideia + SI level + tipo de projeto.
  3. Execute /grill-me → o agente vai entrevistar sem piedade. Respondam honestamente — requisitos falsos colapsam aqui.
  4. Salve o Q&A em 01-grill.md (o agente faz isso automaticamente via harness-define).
  5. Execute /to-prd → revise o PRD gerado. O que está errado? O que está faltando?

📌 Anote: qual foi a pergunta do grill que mais mudou sua visão do projeto?

Capstone · Debrief · 5 min

O que cada grupo descobriu

🔐

Qual foi o SI level?

Por quê esse nível? O que muda no fluxo com nível c ou d?

🔍

Que tipo foi detectado?

Pipeline teve +10 perguntas? O que a detecção de tipo mudou no grill?

💡

A pergunta que mudou tudo

Qual pergunta do grill mais mudou a visão de vocês sobre o projeto?

Síntese: o /grill-me é onde os requisitos falsos colapsam. Você saiu com um PRD mais honesto do que teria escrito sozinho — sem o agente te confrontar.

Módulo 12 · As 3 Leis

As 3 leis do harness

I

Estrutura > Prompting

CLAUDE.md + rules bate prompt engineering toda vez. Um invariante declarado vale mil "seja cuidadoso".

II

O Ratchet

Toda falha é uma rule esperando ser escrita. Harnesses não regridem — cada erro sobe um dente.

III

Gates não são opcionais

Ship only green. /validar + revisor-codigo não são sugestões — são a porta de saída de cada task.
