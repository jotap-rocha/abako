THREAD DE SI — atravessa todas as fases: assessment na fase 1, aplicado nas regras do harness, checado no gate e no revisor, arquivado no ship

Cada fase grava artefato em .claude/projetos/{slug}/ — o STATUS.md sempre reflete em qual fase o projeto está.

Fase 1

O ponto de entrada — /novo-projeto

Primeira coisa a rodar em qualquer projeto. Orquestra o onboarding e garante que o contexto certo seja capturado antes de qualquer código.

Pergunta 1

"Qual é a ideia?" — descrição livre em linguagem natural. Sem template, sem formato obrigatório.

Pergunta 2 — SI Assessment

Classsifica o nível de segurança da informação: a = público · b = interno · c = confidencial · d = restrito

Pergunta 3 — Tipo

app · pipeline-local · pipeline-cloud · outro — determina qual conjunto de regras e KBs o harness-architect vai gerar.

Artefatos criados

.claude/projetos/{slug}/STATUS.md — .claude/projetos/{slug}/00-ideia.md

O STATUS.md é o dashboard do projeto: fase atual, checklist de fases, nível SI. Todos os agentes harness-* o atualizam ao final da sua execução.

Fase 2

Entrevista implacável — /grill-me

O skill que interroga a ideia até que nenhuma ambiguidade sobreviva. Sem grill, a PRD fica vaga. Com grill, os critérios de aceite se escrevem sozinhos.

Como funciona

  • Lê o 00-ideia.md gerado pelo /novo-projeto
  • Faz perguntas de desambiguação em série — não segue em frente sem resposta
  • Para projetos pipeline-*, o harness-define aplica 10 perguntas obrigatórias de pipeline antes de encerrar
  • Resultado salvo em 01-grill.md

Exemplo de pergunta de grill

"Você disse 'relatório diário'. Quem consome esse relatório — um humano ou um sistema downstream? Se humano: qual é o formato esperado (PDF, email, dashboard)? Se sistema: qual é o contrato de schema?"

Pipeline: 10 perguntas extras

Fonte dos dados, frequência, volume estimado, SLA de latência, idempotência, schema evolution, destino, orquestrador, observabilidade, rollback.

O harness-define consolida as respostas do grill e grava 01-grill.md — a matéria-prima do PRD.

Fase 3

O PRD — especificação que não gera dúvida

Gerado pelo /to-prd a partir do 01-grill.md. Salvo em 02-prd.md. Tudo que vai para tasks precisa estar aqui — se não está no PRD, não existe como task.

Problem Statement

O que dói hoje? Para quem? Qual a consequência de não resolver?

Solution

O que vamos construir. Escopo fechado — não "melhorar", mas "implementar X com comportamento Y".

User Stories + Critérios Testáveis

Cada story tem critérios de aceite verificáveis. "Responde em SSE", não "ser rápido". O que não é verificável não entra.

Out of Scope

Explícito sobre o que NÃO será construído nessa iteração. Evita scope creep silencioso.

SI Considerations

Baseado no nível SI do assessment. Nível d = requisitos de segurança vão para critérios de aceite obrigatórios.

O PRD é o único documento que o /to-tasks lê para gerar tasks. PRD ruim = tasks ambíguas = gate vermelho.

Fase 4

O canônico começa mínimo — /harness-architect gera o resto

O que o canônico tem desde o clone zero

  • ✓Regras de SI (seguranca.md) — carregam sempre
  • ✓Skills de workflow (grill, prd, tasks, ship, handoff)
  • ✓9 agentes universais (revisor-codigo, harness-define, harness-build, harness-ship, ...)
  • ✓Gate Stop hook (ruff + mypy + pytest)
  • ✓Definição de pronto (definicao-de-pronto.md)

O que o /harness-architect gera para o projeto

  • +Agentes de domínio (agents/domain-expert.md)
  • +KBs de stack (kb/fastapi/, kb/langgraph/)
  • +Regras de stack path-scoped (rules/agente.md)
  • +.mcp.json real com connection string preenchida
  • +CLAUDE.md preenchido com stack, layout, invariantes

Para projetos pipeline-*

O /harness-architect também gera: rules/pipeline.md, rules/schema-evolution.md, agente pipeline-architect, KB de orquestrador escolhido (Airflow/Dagster/DLT), e perguntas de pipeline embutidas no harness-define.

Fase 5

Backlog local ou GitHub?

/to-tasks vs /to-issues — ambos leem o PRD e geram tasks com os mesmos campos obrigatórios.

Critério /to-tasks /to-issues
Onde viveArquivos .md em tasks/GitHub Issues com label ready-for-agent
StatusAtualizado no próprio arquivo (frontmatter)Label trocada na issue (open/closed + labels)
VisibilidadeLocal — só quem tem o repoGitHub — times distribuídos, stakeholders
Rastreabilidadetasks/README.md como índiceGitHub Projects board automático
Quando usarSolo dev, projetos internos, protótiposTimes, projetos abertos, aprovação humana

Campos obrigatórios em toda task

  • Status (not-started / in-progress / done)
  • Blocked by (task-NN ou vazio)
  • O que construir (descrição fechada)
  • Critérios de aceite testáveis

Índice

Independente do método, 04-tasks-index.md é salvo em .claude/projetos/{slug}/ com o sumário de todas as tasks e seus status iniciais.

Fase 6a

O loop de implementação — harness-build

Agente que executa as tasks uma a uma, com gate e revisor obrigatórios antes de fechar cada uma.

1. Ler task

Lê a task atual, verifica bloqueadores. Se blocked by ≠ done, pula para próxima task desbloqueada.

↓

2. Implementar

Código + testes unitários. Nada de scope creep — só o que está na task.

3. Gate /validar

ruff check + mypy + pytest — verde para continuar. Se vermelho, corrige e tenta de novo. Tentativas registradas em metrics/entregas.jsonl.

↓

4. Revisor revisor-codigo

Subagente analisa o diff contra as rules. Veredito: aprovado ou c/ ressalvas. Se bloqueado, não fecha a task — corrige e repete gate + revisor.

5. Commit + fecha task

Commit no formato feat(task-NN): titulo. Task marcada como done. Uma linha JSON appended em metrics/entregas.jsonl.

Gate e revisor são OBRIGATORIOS — task só fecha com ambos verdes. Não há atalho.

Fase 6b · Encerramento

Encerrar com evidência — harness-ship

Quando todas as tasks estão done, o harness-ship fecha o projeto com retrospectiva mensurável e artefatos arquivados.

/scorecard

Lê metrics/entregas.jsonl e exibe: tasks entregues, taxa de autonomia, mediana de tentativas no gate, distribuição de vereditos do revisor.

05-retro.md

Escrito pelo harness-ship. Contém métricas da entrega, decisões tomadas (com link para ADRs), o que funcionou, o que não funcionou, próximos passos recomendados.

STATUS.md fechado

Fase marcada como "shipped" com data. Projeto arquivado — não aparece mais na lista de projetos ativos.

ADRs arquivados

Decisões técnicas contestáveis registradas em docs/adr/ durante o build são referenciadas na retro. Ficam no repo para consulta futura.

O que NÃO é o ship

Não é deploy em produção (isso é CI/CD). Não é apresentação para stakeholders. É o encerramento do ciclo do agente — evidência de entrega, não celebração.
