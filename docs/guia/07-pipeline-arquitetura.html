Visão geral

Pipeline não é só ETL

Um pipeline maduro tem 4 dimensões que trabalham juntas:

🥉

Medallion

Raw → Bronze → Silver → Gold com responsabilidades claras por camada

🔗

Lineagem

De onde o dado veio + o que aconteceu com ele em cada transformação

📋

Contratos

Acordo formal produtor → consumidor em ODCS YAML versionado

📊

Observabilidade

Structured logs + alertas + dashboards — o pipeline que se explica

Princípio: Um pipeline sem lineagem é uma caixa preta. Um pipeline sem contrato é uma promessa não documentada. Um pipeline sem observabilidade só falha na produção.

Medallion

As 4 camadas — responsabilidades e colunas obrigatórias

Camada Responsabilidade NUNCA fazer Colunas obrigatórias
Raw Cópia exata, imutável do dado da fonte Transformar, deletar, sobrescrever _source_file, _ingest_ts
Bronze Tipagem + metadata de lineage Lógica de negócio, agregações _ingested_at, _source, _run_id, _batch_id
Silver Limpeza + deduplicação + validação Agregar, calcular KPIs _processed_at, _pipeline_version
Gold Agregações de negócio prontas para consumo Lógica de limpeza, deduplicação _updated_at

Raw é sagrado: nunca modifique, nunca delete. É o backup histórico de tudo que chegou.

Schema enforcement: começa no Bronze. Sem tipagem = sem confiança nas camadas acima.

Bronze

Metadados de lineage no primeiro toque

# Bronze — não só tipagem, mas rastreabilidade desde o início
bronze_df = raw_df.select(
    col("id").cast("string").alias("order_id"),
    col("amount").cast("decimal(10,2)"),
    col("created_at").cast("timestamp"),
) \
.withColumn("_ingested_at", current_timestamp()) \
.withColumn("_source", lit("erp-orders")) \
.withColumn("_run_id", lit(run_id)) \
.withColumn("_batch_id", lit(batch_id))

Princípio 1 — Raw é sagrado

Nunca modifique a camada Raw depois da ingestão. Ela é a fonte de verdade imutável. Se precisar reprocessar, releia do Raw e recrie o Bronze.

Princípio 2 — Schema enforcement

Defina schema explícito no Bronze. Dado sem schema = dado sem contrato. Use StructType no Spark ou table schema no Unity Catalog. Rejeite dados que não conformam.

Colunas obrigatórias

_ingested_at_source_run_id_batch_id

Schema Evolution

Schema mudou — o que fazer?

Árvore de decisão

Schema detectado ≠ esperado?
├── Mudança ADITIVA (nova coluna nullable)?
│   ├── strategy=merge
│   │   └── mergeSchema → processa normalmente
│   └── strategy=quarantine
│       └── quarantine + notify
├── Mudança BREAKING (tipo mudou, coluna sumiu)?
│   └── quarantine + notify_owner (sempre)
└── Violação de CONTRATO DECLARADO?
    └── fail (exceção) + log estruturado + ADR

merge — mudança aditiva

df.write.option("mergeSchema", "true")
   .mode("append").saveAsTable(table)

quarantine — suspeito

send_to_quarantine(df, reason="schema_mismatch")
notify_owner(config, reason="schema_mismatch")

fail — violação de contrato

raise ContractViolationError(
    f"Campo {field} removido — breaking change"
)
Quarantine

Quarantine — preservar o dado, investigar o problema

Estrutura da tabela de quarantine

{catalog}.bronze.quarantine

ColunaDescrição
_quarantine_reasonschema_mismatch, null_violation...
_quarantine_tsTimestamp do envio para quarantine
_run_idRastreabilidade do run
_contractContrato violado (ex: orders-v1)
_raw_dataJSON original do dado problemático
 
send_to_quarantine(
    df,
    reason="schema_mismatch",
    run_id=run_id,
    config=config
)

Regra de ouro: nunca delete dados em quarantine. Eles são evidência do problema. Quando reprocessar, adicione _reprocessed_at — nunca remova o registro original.

Contratos

Contrato de dados — acordo formal

# ODCS — Open Data Contract Standard
id: "orders-contract-v1"
version: "1.0.0"
producer: {team: data-engineering}
consumer: [{team: analytics}]
schema:
  fields:
    - {name: order_id, type: string,
       required: true, unique: true}
    - {name: amount, type: "decimal(10,2)",
       min: 0.01}
sla:
  freshness: "< 24 hours"
quality:
  completeness: "> 99%"
versioning:
  breaking_changes:
    - remove_column
    - rename_column
    - change_type

Regras de versionamento

MudançaEstratégia
v1 → v1.1 (nova coluna nullable)mergeSchema
v1 → v2 (coluna removida)quarantine + ADR + notify
v1 → v1.1 (tipo alterado)quarantine + notify

O contrato vive junto ao código. Versione em Git. Valide no pipeline no momento da ingestão. Violação = quarantine imediato.

SLA como contrato

freshness: "< 24 hours" não é aspiração. É obrigação monitorada com alerta automático quando violada.

Observabilidade

Structured logging — o pipeline que se explica

log.info("pipeline_step_completed",
    pipeline="orders_pipeline",
    layer="bronze",
    run_id=run_id,
    records_in=1000,
    records_out=987,
    records_quarantined=13,
    duration_ms=1200,
    source="s3://bucket/orders/"
)

Métricas por step

records_inrecords_outrecords_quarantinedduration_msnull_rate

Nunca em logs

  • CPF, email, nome, telefone

  • Dados financeiros individuais

  • Qualquer dado classificado como PII

records_in - records_out = anomalia a investigar. Se a diferença for maior que o esperado, dispare alerta antes de concluir o step.

run_id em tudo: é o fio que conecta logs → quarantine → alertas. Sem run_id, debugar em produção é impossível.

Grill obrigatório

10 perguntas obrigatórias antes do PRD de pipeline

1. Fontes — De onde vêm os dados? (sistema, formato, frequência)

Define se é batch, streaming ou híbrido

2. Schema — Estável ou pode mudar sem aviso?

Define a strategy de schema evolution

3. Volume — GB/dia? Registros/hora? Backfill histórico?

Define cluster size, particionamento, janela de backfill

4. Sensibilidade — Tem PII? (CPF, email, saúde, finanças?)

Determina mascaramento, restrições de log, compliance

5. SLA — O que "atrasado" significa para o negócio?

Define o contrato de freshness e thresholds de alerta

6. Consumidores Gold — BI? ML? API downstream?

Define o modelo de dados da camada Gold

7. Owner — Quem acorda às 2h se o pipeline quebrar?

Define roteamento de alertas e escalation

8. Ambiente — Local (Spark+Airflow) ou Cloud (Databricks)?

Define config de environments e ferramentas de deploy

9. Qualidade — O que é BLOQUEANTE vs LOG+QUARANTINE?

Define fail vs quarantine vs merge por tipo de anomalia

10. Portabilidade — Multi-tenant? Multi-ambiente (dev/prd)?

Define parametrização de config e isolamento de catalogs
